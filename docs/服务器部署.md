# 社工知识库

Cognee 1.6.6 自建知识库。**原始文件存档 + 转 md 入 vault 与知识库**，Obsidian 浏览，DSH skill 生成文书。

## 目录

```
/srv/social-work/
├── .env                    # 配置（含密码/key，勿外泄）
├── .cognee-key             # DSH skill 用的 Cognee API key（权限 600）
├── .syncthing-key          # Syncthing REST API key（权限 600）
├── docker-compose.yml      # cognee + syncthing 两个服务
├── Dockerfile              # 官方镜像 + 本地 OCR + Office loader
├── entities.yaml           # 实体名册：转换时自动插 [[链接]]
├── feishu-flow.yaml        # 飞书收件箱配置（目录 token / 项目 / 类别）
├── config/
│   └── config.yaml         # 路径与容器名（root / container / key_file / datasets）
├── scripts/
│   ├── config.py           # 读 config/config.yaml（SOCIAL_WORK_ROOT 可覆盖 root）
│   ├── convert-md.py       # 原始文件 → vault 里的 md
│   ├── scan-inbox.py       # 飞书未分类 → 分类 → 转 md → 归档 → 入库（定时跑）
│   └── cognee.py           # 包装 cognee-cli：search / add / cognify / sync
├── syncthing-add-device.sh # 把客户端注册进 vault 同步
├── inbox/                  # 飞书未分类的本地暂存（处理完自动清空）
├── state/manifest.yaml     # 已处理文件台账（幂等 + 变更检测）
├── vault-huadu/            # 花都项目 Obsidian 仓库（md/ + media/）
├── vault-huimin/           # 惠民项目 Obsidian 仓库（md/ + media/）
├── sources/                # 原始文件存档（不入知识库）
│   └── projects/huadu/     # 花都源文件
│   └── projects/huimin/    # 惠源泉文件
└── snapshots/              # 备份快照
```

两个 vault 各自独立：**项目的所有东西（原始文件 + 笔记 + 生成的文书）都在各自项目里**，物理隔离。

## 数据流

```
飞书「未分类」（手机/电脑随时传）
   │  定时（15 分钟）scan-inbox.py 拉取
   ▼
分类（LLM 读内容 → 项目 + 类别）
   │
   ├─ 原件 → sources/projects/<项目>/<类别>/
   ├─ md   → vault-<项目>/md/<类别>/<文档名>.md（顶部带原件链接 + [[实体]]）
   └─ 飞书 → 移到「已分类/<项目>/<类别>/」
   │
   ▼
Cognee 入库 + 建图          →  检索/生成时引用
   │
   ▼
Obsidian（客户端）           →  人看、人改（Syncthing 双向）
```

手动放的原始文件（docx/xlsx/pdf/图片）走同一条路，只是跳过「飞书拉取 + 分类」：放进 `sources/projects/<项目>/`，再跑 `convert-md.py`。

**原始文件只存档，不进知识库**——同一份内容不建两份索引。

## 飞书收件箱（自动归档）

手机或电脑上把文件丢进飞书「社工知识库 / 未分类」，服务器每 15 分钟自动处理一次：**分类 → 转 md → 归档原件 → 建索引**。

```bash
python3 /srv/social-work/scripts/scan-inbox.py             # 手动跑一次
python3 /srv/social-work/scripts/scan-inbox.py --dry-run   # 只报计划不动文件
python3 /srv/social-work/scripts/scan-inbox.py --verbose   # 打印分类理由
```

- 定时任务：`systemctl --user status social-work-scan.timer`（`OnUnitActiveSec=15min`）
- 分类：先走 M2 规则层（`config/project_aliases.yaml` + `config/category_keywords.yaml`），判不了才调 LLM；置信度 < 0.7 的落 `_待确认/`
- 类别：`发票票据` / `项目计划` / `项目执行` / `日常工作佐证` / `政策文件` / `其他`
- 幂等：`state/manifest.yaml` 记 file_token + sha256，重复扫描不会重复入库
- 修改过的文件：飞书侧改完重传（新 file_token）会重新走一遍；服务器侧直接改 md 即可
- **图片默认只存档**（见上面「图片处理」），不 OCR、不调视觉模型

> 隐私：原始文件会同步到飞书云盘（单位与飞书有合作协议）。含服务对象面部/证件的图片不要走这条路。

## 审计与通知

每次 `scan-inbox.py` 运行都会写一条审计记录到 `state/audit/YYYY-MM-DD.jsonl`
（转换失败也会记，不会静默）。

```bash
python3 /srv/social-work/scripts/audit.py                    # 看今天
python3 /srv/social-work/scripts/audit.py --date 2026-11-06   # 看某天
python3 /srv/social-work/scripts/audit.py --date 2026-11-06 --send   # 看某天 + 发飞书
python3 /srv/social-work/scripts/audit.py --json              # 原始统计
```

- **每天 22:00（北京时间）自动发飞书汇总**：`systemctl --user status social-work-audit.timer`
  - timer 写 `OnCalendar=*-*-* 22:00:00 Asia/Shanghai`，systemd 自己换算成 UTC（系统是 `Etc/UTC`）
- 收件人：`config/notify.yaml` 的 `to`（open_id 列表，**不入库**）；
  文件缺失时回落到 `~/.dsh/integrations/dsh-feishu/config.json` 的 `ownerOpenIds`
- 保留期：`audit_log.prune()` 默认 90 天（由 `config/config.yaml` 的 `audit_retention_days` 控制）
- 通知失败**不会**拖垮归档主流程（`notify.send()` 只返回 False）

## 错误队列与兜底

**错误分类**（`scripts/retry.py` + `scan-inbox.py`）：

| 类型 | 例子 | 处理 |
|---|---|---|
| 可重试 | 飞书 API 超时、Cognee 502、LLM 端点抖动 | 指数退避重试 3 次（2s / 4s），仍失败才报错 |
| 不可重试 | 格式不支持、文件损坏、权限不足 | 立即报错，不落库 |
| 需人工 | 分类置信度低、项目判定不了 | 落 `_待确认/`，进兜底清单 |

```bash
cat /srv/social-work/state/errors/open.yaml     # 未处理的错误
python3 /srv/social-work/scripts/fallback.py --list                  # 待兜底条数
python3 /srv/social-work/scripts/fallback.py --date 2026-11-06       # 生成清单 md
```

- **主动告警**：本轮出现**新**错误就立刻发飞书（重复运行不会重复告警 —— 同一 `(file, error)` 只入队一次）
- **坏文件不会无限重试**：已有未处理错误的文件会被跳过，处理完用 `fallback.py --log` 记录后关闭
- **错误队列**：`state/errors/open.yaml`（未处理）+ `state/errors/YYYY-MM-DD.jsonl`（全量流水）
- **兜底清单** `fallback.py` 会写死边界：LLM 只能判断项目/类别、改名、写说明；
  **不能**决定隐私相关的事，**不能**直接往 `sources/` 写或改原件

## 一条命令归档（M5）

```bash
python3 /srv/social-work/scripts/archive.py --file <路径> [--project huimin] \
                                            [--action auto|ocr|archive_only|vision]
```

- 内部：定项目（给了就用，没给按规则判，**判不了报错退出不猜**）→ 放进 `inbox/` 对应位置
  （`要OCR/` `要识图/` 目录即授权）→ 跑 `scan-inbox.py` → 校验台账与 md
- **`inbox/` 就是待处理队列**：从飞书拉下来的、`archive.py` 放进去的，都走同一条处理路径。
  手工放进来的文件用 `local-<sha256前16位>` 当台账 key，md 顶部**不带飞书链接**（没有 file_token），
  也不会去飞书「已分类」找对应条目
- 已在 `sources/projects/<项目>/` 的文件：`convert-md.py --project <项目>` + `cognee.py sync`

| 项 | 值 |
|---|---|
| 插件 | `@xmanrui/dsh-im` 5.10.0（`dsh plugin --profile web add`） |

## 配置

路径与容器名集中在 `config/config.yaml`（**放服务器**，与 `.env` 同目录）：

```yaml
root: /srv/social-work          # 服务端根目录
container: social-work-cognee   # cognee 容器名
container_root: /host/social-work
key_file: .cognee-key            # 相对 root
audit_retention_days: 90
datasets: {huadu: huadu, huimin: huimin}
llm: {provider: openai, model: <模型名>, endpoint: "", api_key_env: LLM_API_KEY}
```

- 换机器只改这里，脚本里没有硬编码路径
- 环境变量 `SOCIAL_WORK_ROOT` 覆盖 `root`；`SOCIAL_WORK_CONFIG` 指定配置文件路径
- 三个脚本都支持 `--config <path>`
- 查找顺序：`SOCIAL_WORK_CONFIG` → `<root>/config/config.yaml`（脚本上一级）→ `/srv/social-work/config/config.yaml`
- **默认值必须保持 `root=/srv/social-work`、`container=social-work-cognee`**，否则现有 systemd 定时任务会失效

## 转换原始文件

```bash
python3 /srv/social-work/scripts/convert-md.py --project all              # 增量（两个项目 + 共享）
python3 /srv/social-work/scripts/convert-md.py --project huimin --dry-run # 只报计划
python3 /srv/social-work/scripts/convert-md.py --project huimin --force   # 忽略时间戳全转
```

| 源格式 | 走哪条路 | 产物 |
|---|---|---|
| `.docx` | pandoc（快，0.05–0.9 s/份） | md + `media/imageN.jpg` |
| `.xlsx` `.pptx` `.pdf` `.csv` `.xls` `.ppt` `.odt` `.ods` `.rtf` `.html` | docling（容器内，~7 s/份） | md + `media/` |
| `.md` `.txt` | 直接复制 | md |
| 图片 / 音频 / 视频 | 直接复制到 `vault-<proj>/media/` | 原文件（Obsidian 原生支持） |

- 产物位置：`vault-<proj>/md/<源文件相对目录>/<文档名>/<文档名>.md`
- 增量：源文件比产物新才重转
- 转换时按 `entities.yaml` 自动插 `[[实体]]` 链接（改完名册重跑即可）
- `--prune` 可删掉源文件已不存在的 md

> 原始文件**不用** `chmod`——只有 Cognee 要读的 md 才需要 644。

## 入库

```bash
# 1. 先转 md（见上）
# 2. 入库 + 建图（两步都要，缺 cognify 检索不到）
python3 /srv/social-work/scripts/cognee.py add <md 文件> --dataset <数据集>
python3 /srv/social-work/scripts/cognee.py cognify --dataset <数据集>
```

> `add` **不支持目录**：传目录会把目录路径当纯文本存进去。要批量入库用 `sync`（见上），
> 它会自己遍历 md 目录、按 `(name, contentHash)` 增量去重。

### 全量同步（推荐）

```bash
python3 /srv/social-work/scripts/cognee.py sync /srv/social-work/vault-huimin --dataset huimin --dry-run  # 先看计划
python3 /srv/social-work/scripts/cognee.py sync /srv/social-work/vault-huimin --dataset huimin
```

`sync` 是幂等的，按 `(文件名, 内容 md5)` 比对数据集与磁盘：

- 内容变了的旧条目 → 删掉重加；本地已删的 md → 对应条目删掉；重复条目 → 只留一条
- **没变的 md 跳过**（不重加、不重复 cognify）
- **图片等非文本条目不动**
- 连跑两次，第二次应该是「清理 0 个 / 入库 0/N（跳过未变 N）」

## 检索

```bash
python3 /srv/social-work/scripts/cognee.py search "低保申请条件" --dataset huadu
python3 /srv/social-work/scripts/cognee.py search "张某的情况" --dataset huadu --type GRAPH_COMPLETION
python3 /srv/social-work/scripts/cognee.py search "惠民做了什么" --auto-dataset
```

- `--type` 默认 `auto`，按查询形态自动选：含日期（`2026年`、`11月`、`11-05`）→ `TEMPORAL`；
  带引号 → `CHUNKS_LEXICAL`；其余 → `CHUNKS`。只有要自然语言回答（走 LLM、引用来源）才显式传
  `GRAPH_COMPLETION`
- `--auto-dataset` 按查询里的项目关键词（`config/project_aliases.yaml`）选数据集；
  并列或没命中就搜全部。跨项目问题别加
- ⚠️ `TEMPORAL` 明显慢于 `CHUNKS`（实测一次 >60s）；只是问事实就别为了「带日期」触发它

## 图片处理

图片默认**只存档**：不 OCR、不调视觉模型、不生成 md。
是否 OCR 由**所在目录**决定（`config/image_policy.yaml`）：

```
飞书「未分类」/ 下：
  要OCR/     → 本地 OCR 后转 md（vault 里能搜到图片上的字）
  要识图/    → 视觉模型识别（默认 enabled: false）
  其他(含根) → 只存档：原件进 sources/，副本进 vault-<项目>/media/<类别>/
```

- 图片**不会**自动进 Cognee；要检索图片内容，把图片放进「要OCR/」再跑一次 `scan-inbox.py`
- 生活照片没有 OCR 价值，主要靠文件名检索（`<拍摄日期>-<关键词>.jpg`）
- 只存档图片按拍摄日期命名，同一天多张自动加 `-2`/`-3` 序号，不会互相覆盖
- **含服务对象面部/证件的图片不要放进「要OCR/」或「要识图/」**（OCR 在本地，视觉模型会把内容发到外部 LLM）

> ⚠️ `.env` 里的 `IMAGE_OCR_ENABLED` / `IMAGE_EXTRACTION_ENABLED` 在代码里**没有任何引用**，
> 是死配置。图片是否 OCR 只由 `config/image_policy.yaml` 决定。

> ⚠️ 本地 OCR 用容器里的 `rapidocr` 包。镜像装的是 `rapidocr>=3.9.1`；
> 早先装的 `rapidocr-onnxruntime` 只提供 `rapidocr_onnxruntime` 模块，`import rapidocr` 会失败，
> 而 `ocr_image()` 在失败时**静默返回空字符串**（`scan-inbox.py:280-281`）——
> 表现是「图片 OCR 出来是空的」，不会报错。排查：进容器跑一遍 `OCR_SCRIPT`。
> `OCR_SCRIPT` 用的是 rapidocr 3.x 的 `RapidOCROutput.txts`（旧版是 `(result, elapse)` 元组），
> 换 rapidocr 大版本时这里要跟着改。

## 客户端同步（Syncthing）

两个 vault 各自作为一个 Syncthing 文件夹，双向同步到客户端的 Obsidian。服务器端不需要装任何东西。

- 服务器设备 ID：`ZYRRRWF-7YSKMUN-2RXPYOQ-W65CACA-JV5FFTP-2IPWC4Z-R6LV4UQ-NYNHUAL`
- 监听端口：`<服务器IP>:22000`（tcp+udp，Oracle Cloud 安全列表里开这个）
- 管理界面：`http://127.0.0.1:8384`（仅本机可访问，需 API key）
- 文件夹：`huadu-vault`（社工 vault · 花都）、`huimin-vault`（社工 vault · 惠民）
- 同步忽略：`.obsidian/workspace*`、`.trash/`、`*.tmp`
- 版本控制：**回收站模式**（`trashcan`），删除的文件进 `.stversions/`，保留 30 天后自动清理

> **版本控制只对「从别的设备收到的变更」生效**（官方文档原文）。所以服务器端归档的是客户端删掉的文件；客户端那边也要开同样的选项，才能保护服务器删掉的文件。两边都开才完整。

客户端加入：

```bash
# 在客户端机器上执行；<设备ID> 从 Syncthing Web UI 首页复制
ssh ubuntu@<服务器IP> 'bash -s' < syncthing-add-device.sh <设备ID>
```

脚本会把该设备同时注册进两个文件夹的共享。之后在客户端 Syncthing 界面分别对两个文件夹点「添加」，各自指向一个本机目录（Obsidian 里作为两个独立仓库打开）。

> 不要用 Obsidian Self-hosted LiveSync / CouchDB：那是「两端都是 Obsidian」的方案，服务器端没有 Obsidian 进程，AI 写进 vault 的文件永远推不到客户端。

## 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 检索不到刚加的文件 | 没建图 | 跑 `cognify` |
| 转换出的 md 检索不到 | 转完没入库 | `add` + `cognify` |
| 图片没变成 md | 图片本来就不转 | 图片直接复制到 `vault-<proj>/media/`，Obsidian 原生支持 |
| 入库报 Permission denied | 文件权限 600 | `chmod 644` |
| 入库报 No loader found | 缺 Office loader | 确认用的是 `cognee-ocr:local` 镜像（见 Dockerfile） |
| docling 报 `No OCR engine found` 之外还带 `ModuleNotFoundError: No module named 'torchvision'` | 镜像缺 torchvision，**文本层的 PDF 也转不了** | 用重建后的 `cognee-ocr:local`。注意 torchvision 必须和 torch 同源：镜像里 torch 是 `2.14.1+cpu`，torchvision 要从 `download.pytorch.org/whl/cpu` 装 `0.29.1+cpu`；装 PyPI 的 0.29.2 会报 `operator torchvision::nms does not exist` |
| docling 报 `ModuleNotFoundError: No module named 'docling_ibm_models'` | 镜像缺 docling-ibm-models（表格模型 v1 在 `__init__` 里 import 它，跟开不开表格提取无关） | 同上，Dockerfile 里已加 `docling-ibm-models>=3.9.1,<5` |
| 图片 OCR 出来是空字符串 | 容器缺 `rapidocr` 包（`ocr_image()` 失败时返回 `""` 不报错） | 确认镜像装的是 `rapidocr` 而不是 `rapidocr-onnxruntime`；进容器手动跑 `OCR_SCRIPT` 看真实报错 |
