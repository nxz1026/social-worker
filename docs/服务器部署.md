# 服务器部署

> 面向运维。当前架构：**项目-活动-材料生产线**，不再是早期的「飞书归档+转md+建索引」。
> 部署目录 `/srv/social-work`，开发目录 `/home/ubuntu/DSH/social-worker`，**两者是独立副本**。

## 1. 服务清单

单元文件在仓库 `deploy/systemd/`，安装方式见该目录的 README。

| 单元 / 容器 | 作用 | 端口 |
|---|---|---|
| `social-work-api.service` | FastAPI 后端 | `127.0.0.1:8001`（仅本机） |
| `social-work-readme.timer` | 每 15 分钟刷新活动/项目索引 md + docx 骨架 | — |
| `social-work-feishu.timer` | 每小时把 projects/ 镜像到飞书云文档 | — |
| `social-work-audit.timer` | 每天 22:00 发审计摘要 | — |
| 容器 `social-work-cognee` | 图谱与向量检索 | `127.0.0.1:8000` |
| 容器 `social-work-syncthing` | 项目资料双向同步到 Obsidian | `8384`(UI) / `22000`(同步) |

**nginx 对外**：`443` → `/sw/`（Web 界面）、`/sw-api/`（API 反代到 `127.0.0.1:8001`）

## 2. 部署流程

**改完代码必须跑**（仓库与生产是两个目录）：

```bash
cd /home/ubuntu/DSH/social-worker
./deploy.sh              # rsync api/engine/scripts/config/web → /srv/social-work 并重启
./deploy.sh --dry-run    # 只列出会改哪些文件
```

`deploy.sh` 的校验顺序：

1. **部署前资产验收**（最先跑）：确认模板与项目数据在场，并跑 9 个资产类
   测试文件（99 项），**任何跳过都算失败**。不通过直接中止，生产不动。
2. 同步代码 → 重启服务
3. **路由数校验**（< 30 视为失败，说明服务没起来）

资产验收放在同步**之前**是有意的：验收只依赖模板与项目数据，与代码版本无关，
前后跑结果一样；放在前面就能做到「不通过就不部署」。放在后面的话新版本已经
对外服务了，失败只能报错、拦不住。

资产验收失败时脚本会打印「资产验收未通过，已中止部署（生产未改动）」并以
非零码退出。**注意 `deploy.sh` 用的是 `if ! cmd; then` 而不是 `cmd; va=$?`** ——
后者在 `set -e` 下永远不会执行到判断分支，那句关键提示会变成死代码（审计 R-05）。

### 为什么资产验收要单独一道

模板和业务数据**不入 git**（合规要求），所以干净检出天然缺资产、相关测试会 skip。
若只跑 `pytest`，在有资产的机器上是 **779 passed**、在干净环境是 742 passed + 36 skipped，
两者都「全绿」，无法区分。

`verify_assets.py` 把 skip 变成显式失败：

```bash
# 部署机上跑（deploy.sh 自动调用）
SOCIAL_WORK_TEST_REPO=/home/ubuntu/DSH/social-worker \
  python3 /srv/social-work/scripts/verify_assets.py

# 只查资产
python3 scripts/verify_assets.py --assets-only
```

退出码：0 全通过（无跳过）；1 资产缺失 / 有测试被跳过 / 有测试失败。

**测试代码只在开发仓**，生产目录不同步 `tests/`，所以要用 `SOCIAL_WORK_TEST_REPO`
指向开发仓；不设会报「找不到测试目录」并失败（不静默通过）。

**不跑 deploy.sh 的后果**：systemd 服务仍跑旧代码，新端点 404。

## 4. 数据库

PostgreSQL 18，库 `socialwork`，用户 `admin`。

| 表 | 用途 |
|---|---|
| `users` | 账号（`real_name` 真实姓名） |
| `user_projects` | 项目授权（`access` = readonly/write） |
| `sessions` | Web 登录态（12 小时） |
| `api_keys` | Agent 用 Key（`key_hash` 认证 + `secret_enc` 展示） |
| `audit_log` | 操作审计（含材料核对/签字记录） |

### 4.2 审计保留策略（待定）

`audit_log` 当前**无自动清理**，行数只增不减（2026-11-21 实测 1497 行，约 200KB）。
按当前写入频率（每天几十条）估算，一年约 1-2 万行，占用可控。

**保留期限尚未确定**，等实际使用一段时间后再定。可能的口径：

| 口径 | 说明 |
|---|---|
| 永久保留 | 最省事，磁盘压力小，适合当前量级 |
| 按年归档 | 每年把旧记录导出到 `state/audit/YYYY.jsonl` 后删除 |
| 按类型分级 | 材料核对/签字记录永久保留，其他操作（登录、浏览）保留 1 年 |

**注意**：材料核对与签字记录属于业务凭证性质，若将来做分级清理，
这两类应优先保留——它们回答的是「谁在什么时候确认了这份材料」。

清理脚本尚未编写；真要实施时必须先备份，且不能删掉未结项项目的记录。

**DSN 在 `/srv/social-work/.env.service`**，systemd 单元通过 `Environment=` 注入。

### 4.1 数据库权限坑（重要）

`admin` 是**普通角色**，`public` schema 的 `CREATE` 权限在 PG 15+ 已默认收回。
建表需用 postgres 超级用户，通过 peer 认证：

```bash
docker run --rm -i --privileged --pid=host -v /:/host alpine:latest \
  chroot /host su -s /bin/sh postgres -c 'psql -d socialwork' < /tmp/ddl.sql
```

**两个坑**：
1. `/home/ubuntu` 权限 750，postgres 进不去 → **必须用 stdin 管道**，不能 `-f 文件路径`
2. 新建表 owner 是 postgres，admin 读写不了 → 建完要 `ALTER TABLE ... OWNER TO admin`

```bash
curl -s -H "X-API-Key: $K" http://127.0.0.1:8384/rest/config/folders
```

## 6. LLM 配置

`config/api.yaml` 的 `llm` 段只有三个必填项：

```yaml
llm:
  base_url: https://api.longcat.chat/openai/v1
  model_id: LongCat-2.5
  api_key: ak_xxx
```

**环境变量优先**：`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL_ID`。

文风在 `config/llm_style.yaml`：`务实`（默认）/ `平实` / `党建`，每种配样例文件与硬性要求。

## 7. CORS 配置

CORS 来源在 `config/api.yaml` 的 `server.cors_origins`：

```yaml
server:
  cors_origins:
    - "https://<公网IP>"          # 公网 Web 界面（自签证书）
    - "http://127.0.0.1:8001"     # 本机直连调试
```

真实公网 IP 只写在服务器本地 `config/api.yaml`（该文件不进 git），文档一律用
`<公网IP>` 占位。

**生产必须收敛为显式 allowlist，不要用 `"*"`。** `"*"` 等于允许任意站点在浏览器里
带着用户 Cookie/Token 调 API。改完跑 `./deploy.sh` 同步 `config/` 并重启服务。

### 7.1 通配来源在生产环境会被拒绝启动

`api/settings.py` 在 `SOCIAL_WORK_ENV=production` 且来源为 `["*"]` 时**直接抛错**：

```
RuntimeError: 生产环境（SOCIAL_WORK_ENV=production）不允许 CORS 通配来源 *。
请在配置文件里把 server.cors_origins 改成显式 allowlist……
```

这是 2026-11-22 从「仅告警」改过来的 fail-closed：原来漏配一次就静默放行，
等于把 API 暴露给任意站点（审计 C-05）。

**确需通配**（例如内网全同源反代）时，显式设环境变量放行，把风险变成一次有意识的决定：

```bash
# deploy/systemd/social-work-api.service 的 Environment= 里加
Environment=SOCIAL_WORK_ALLOW_WILDCARD_CORS=1
```

此时仍会打警告日志：

```bash
journalctl --user -u social-work-api.service | grep CORS
```

新增前端来源（换域名、加端口）时同步加一行；漏加的表现是浏览器报
`No 'Access-Control-Allow-Origin' header`，而 curl 直连正常。

## 8. 常用运维

```bash
# 服务状态
systemctl --user status social-work-api.service
systemctl --user list-timers 'social-work*'

# 重启后端
systemctl --user restart social-work-api.service

# 手动刷新索引
python3 /srv/social-work/scripts/refresh_readme.py

# 手动核对活动
python3 /srv/social-work/scripts/check_activity.py --all

# 照片压缩（存量）
python3 /srv/social-work/scripts/compress_photos.py --dry-run
python3 /srv/social-work/scripts/compress_photos.py

# 飞书同步（手动触发）
python3 /srv/social-work/scripts/sync_feishu.py

# 生成 API Key
curl -X POST -H "x-token: <session>" -H "Content-Type: application/json" \
  -d '{"user":"admin","name":"agent","expires_days":365}' \
  http://127.0.0.1:8001/api/sw/keys
```

## 9. 排障

| 现象 | 排查 |
|---|---|
| 新端点 404 | 没跑 `deploy.sh`，服务还是旧代码 |
| API 401「登录已过期」 | session 12 小时到期，重新登录 |
| Key 无法查看明文 | Key 签发于加密改造前，`secret_enc` 为 NULL，需重签 |
| 签发 Key 报「未安装 cryptography」 | `pip install cryptography`；仅在明确接受弱加密时才设 `SOCIAL_WORK_ALLOW_WEAK_KEYSAFE=1` |
| Obsidian 看不到文件 | 检查 `.stignore` 是否排除了该类型 |
| 同步不动 | `curl -X POST -H "X-API-Key: $K" "http://127.0.0.1:8384/rest/db/scan?folder=<id>"` |
| Cognee 无响应 | `docker logs social-work-cognee --tail 50` |
| 飞书同步报「N rel_path(s) map to multiple Drive entries」 | 云端有同名重复，先清重再推 |
| 飞书出现 .obsidian/.stfolder | 暂存推送已从源头挡住；历史残留由 `_prune_feishu_meta` 清理 |
