## 2. 完成范围

### 2.1 文档生命周期（只读状态）

- 列表：项目 / 类别 / 健康状态 / 文件名关键词筛选，四类状态徽章
  （原件缺失、飞书缺失、索引过期、未索引）
- 详情五个子页：概览、源文件、飞书、索引、关系
- 源文件：路径、大小、sha256、**下载**（按项目鉴权 + 逐次写审计）
- 飞书：状态（已归档/已补传/已移动/已删除/缺失）、file_token、上传时间、跳转链接
- 索引：Cognee 条目名、contentHash、同名条目数、是否过期
- 关系：`[[实体]]` 按类型分组 + **反链**（谁写了 `[[这一篇]]`）+ **共享实体**（谁和我提到同一个实体）
- md 正文在线编辑（editor 及以上），保存后触发一次对账

### 2.2 管理动作（admin）

- 飞书：**重新上传**（换新 file_token）、**删除副本**（本地不动）
- 索引：**重建**（按项目数据集跑 reconcile，幂等）
- 待确认：**归档到指定项目**、**丢弃**（进 `sources/.trash`）、**清理残留**
- 回收站：列出 md / 源文件两类回收站，**恢复**（挪回原位并自动对账）、**彻底删除**
- 文档删除（原就有，改为 admin 专用）

### 2.3 Portal 告警接入

- Portal 的每条社工告警都带 `action: {label, url}`，前端渲染成按钮：
  - 待确认 / 失败 → `/sw/#/pending`（有台账键则直达 `#/doc/<token>/overview`）
  - 索引不可用 / 过期 → `/sw/#/docs?health=index_missing`
  - Syncthing 报错 / 设备全离线 → `/sw/#/pending`
  - 已归档残留 → `/sw/#/pending`（标签「去清理」）
- `/sw/` 支持 hash 深链，**登录后恢复**到原位置，不会被踢回首页：
  `#/docs`、`#/docs?health=...`、`#/pending`、`#/trash`、`#/doc/<token>/<tab>`

### 2.4 用户验收后的补充（2026-11-09 上午）

| 反馈 | 做法 |
|---|---|
| 待确认归档要自动推荐项目 | `/api/issues` 每条 pending 带 `suggested_project` / `suggested_reason`；前端下拉预选并标「（建议）」。规则与 `archive.py` 同一套（文件名优先，判不了读正文），结果按 mtime+size 缓存 |
| 飞书重传要先处理旧副本 | 顺序改为「旧副本改名（`.旧-时间戳`）→ 传新副本 → 删旧副本进飞书回收站」。改名失败直接中止；上传失败把名字改回去；删旧失败只在返回里标 `old_trashed=false`，不影响新副本 |
| 名册缺元素要在界面提醒并告知重建办法 | 关系页顶部黄色提示：缺哪几类（机构/人员/地点）、`entities.yaml` 在哪、怎么填；admin 多一个「重建实体链接」按钮（`POST /api/meta/relink`），补链后自动重建索引 |
| `test_replay` 偶发失败要讲清楚 | 见 §7.1，已修根因（测试间 `SOCIAL_WORK_ROOT` 污染），不再随机挂 |

新增补链能力：`convert-md.py --relink-only`（幂等，只加 `[[实体]]`，不重转、不覆盖正文、跳过 `_待确认`/`.trash`）。名册变更后不必 `--force` 全量重转。

## 3. 关键约束与踩过的坑

- **Cognee `contentHash` 是 md5，台账 `md_sha256` 是 sha256** —— 判「索引过期」必须另算 md5，
  直接比 sha256 会永远判过期。
- **`_待确认` 目录里有 `_md/` 子目录** —— 目录遍历会把「1 个文档」算成「2 个文件」，
  统计时必须剪掉 `_md` 和点开头目录，并按 sha256 去重。
- **audit 日志是回放式** —— 同一文件可能先失败后成功，或先失败后删除；
  统计待确认要看 manifest 的最终状态，不能只看日志里有没有 `pending_review`。
- **源文件下载不能静态暴露 `sources/`** —— 走 `FileResponse` + 项目权限校验 + 审计。
- **`<a download>` 带不了 `x-token`** —— 前端改成 `fetch` + blob 下载。
- **编辑 md 后的 reconcile 是同步子进程** —— 有超时保护；失败不阻断保存，由 15 分钟定时器兜底。
- **门户 `systemctl` 被 NoNewPrivileges 限制** —— 重启门户走它自己的受控接口
  `POST /api/systemd/action`，不能直接 `sudo systemctl`。

### 7.1 `test_classify_rules::test_replay` 为什么之前会随机失败

**它做什么**：拿 6 个真实归档文件回放规则层 —— 用 `scan-inbox.extract` 抽出正文，
再跑关键词规则，断言「判错数 = 0」（判不了允许，交 LLM）。

**表面现象**：单独跑 52 秒通过；跟全量一起跑时，2 张发票被判成「项目执行」，
命中率掉到 50%，`wrong == 0` 失败。

**根因**（不是模型随机，是**测试间全局状态污染**）：

1. `tests/test_api_ops.py` 在 import 时设了 `SOCIAL_WORK_ROOT=<仓库>`（为了让 API
   不连生产库），这个环境变量是进程级的，后面所有测试都受影响；
2. 回放测试再加载 `scan-inbox.py` 时，`_apply_config()` 读到这个变量，
   把根目录设成仓库 `/home/ubuntu/DSH/social-worker`；
3. 真实样本在 `/srv/social-work/sources/projects/...`，转换器判定
   「不在服务端根目录下」直接抛错；
4. 原来的 `_preview_for` 把异常吞成**空串**，于是「没有正文」被当成
   「正文里没有『发票』」⇒ 只按文件名判 ⇒ 判成「项目执行」⇒ 记为**判错**。

**修复**：

- `_preview_for` 取不到预览时返回 `None`（跳过，不算判错），不再用空串冒充正文；
- 回放期间临时把 `SOCIAL_WORK_ROOT` 指向 `/srv/social-work`，结束后恢复，
  保证回放拿到的正文与线上归档时一致；
- 结果：全量跑 190 项全过（45s），回放 6 条、判对 5、判不了 1、判错 0，命中率 83%。
